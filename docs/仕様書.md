# contact-form-sample 仕様書

> このドキュメントは、開発・運用・構築に関わる人向けの設計仕様書です。機能要件、API、データベース、インフラ構成を正確に記述することを目的としています。
> プロジェクトの概要や現在の対応状況（未対応事項など）は [`README.md`](../README.md) を参照してください。

## 1. 概要

静的HTML/CSS/JSのお問い合わせフォームと、Node.js (Express) のAPI、PostgreSQLへのデータ保存を組み合わせたアプリケーション。デプロイ先はAzure完結（Azure Container Apps + Azure Database for PostgreSQL）。

デプロイ済みURL:
- フォーム: https://contact-form-sample.proudwave-93429adb.japaneast.azurecontainerapps.io/
- 問い合わせ一覧: https://contact-form-sample.proudwave-93429adb.japaneast.azurecontainerapps.io/list.html （認証なし、社内確認用）

## 2. 機能要件

### 2.1 お問い合わせフォーム (`/`, `index.html`)

入力項目:

| 項目 | 種別 | 必須 | 制約 |
|---|---|---|---|
| お名前 (`name`) | テキスト | ○ | 1〜100文字 |
| メールアドレス (`email`) | テキスト (email) | ○ | 1〜255文字、`xxx@yyy.zzz`形式 |
| お問い合わせ種別 (`category`) | プルダウン | ○ | 下記4種のいずれか |
| お問い合わせ内容 (`message`) | 複数行テキスト | ○ | 1〜2000文字 |

お問い合わせ種別の選択肢:

| 値 | 表示ラベル |
|---|---|
| `general` | 一般的なお問い合わせ |
| `product` | 製品・サービスについて |
| `quote` | お見積もり・体験のご相談 |
| `other` | その他 |

送信時の挙動:
1. クライアント側で必須・形式チェック（`public/script.js`）。エラーはフィールドごとにインライン表示。
2. `POST /api/contact` にJSONで送信。
3. 成功 (201) → `thanks.html` （サンクスページ）へ画面遷移。
4. 失敗 → フォーム下部にエラーメッセージを表示（画面遷移なし）。

管理者への通知メール送信は行わない設計とし、DB保存のみとしている。

### 2.2 サンクスページ (`/thanks.html`)

送信成功後に遷移する専用ページ。「お問い合わせありがとうございました。」の文言と、フォームへ戻るリンクを表示する。

### 2.3 問い合わせ一覧 (`/list.html`)

- `GET /api/contact` の結果を表形式で表示する（日時・お名前・メールアドレス・種別・内容、直近50件、新しい順）。
- 認証機能は設けていない。小規模な社内・開発確認用途として設計しており、個人情報を含むためURLの外部共有は運用上禁止としている。
- `<meta name="robots" content="noindex, nofollow">` で検索エンジンのインデックスを抑制している。

### 2.4 スコープ外の機能

以下は設計上、対象外としている:

- ユーザー認証・ログイン機能
- 管理者向けメール通知
- 問い合わせへの返信・ステータス管理機能
- Google reCAPTCHA等、外部サービスに依存するスパム対策（7.3節のボット対策を参照）

## 3. API仕様

ベースURL: デプロイ先のオリジン（例: `https://contact-form-sample.proudwave-93429adb.japaneast.azurecontainerapps.io`）

### 3.1 `POST /api/contact`

お問い合わせを1件保存する。

**リクエスト**

```
Content-Type: application/json
```

```json
{
  "name": "山田太郎",
  "email": "taro@example.com",
  "category": "general",
  "message": "お問い合わせ内容です。",
  "hp_website": ""
}
```

`hp_website` はボット対策のhoneypotフィールド（7.3節参照）。人間のユーザーには見えないため通常は空文字で送信される。省略しても動作する。

**レスポンス (成功時 201)**

```json
{
  "contact": {
    "id": 1,
    "name": "山田太郎",
    "email": "taro@example.com",
    "category": "general",
    "message": "お問い合わせ内容です。",
    "created_at": "2026-09-07T10:08:34.616Z"
  }
}
```

**レスポンス (バリデーションエラー時 400)**

```json
{
  "error": "入力内容に誤りがあります。",
  "fields": {
    "name": "お名前を入力してください。",
    "email": "メールアドレスの形式が正しくありません。",
    "category": "お問い合わせ種別を選択してください。",
    "message": "お問い合わせ内容を入力してください。"
  }
}
```
`fields`にはエラーのある項目のみが含まれる。

**レスポンス (サーバーエラー時 500)**

```json
{ "error": "サーバーエラーが発生しました。" }
```

**レスポンス (レート制限超過時 429)**

```json
{ "error": "送信回数が上限に達しました。しばらく時間をおいて再度お試しください。" }
```
同一IPから10分あたり5回を超えて送信した場合に返る。

**honeypot検知時のレスポンス (201、偽装成功)**

```json
{ "contact": null }
```
`hp_website` に値が入っている場合、実際にはDBへ保存せずこのレスポンスを返す設計（ボットに検知されたと悟らせないため）。

### 3.2 `GET /api/contact`

保存済みの問い合わせを新しい順に最大50件返す（`list.html`が利用）。

**レスポンス (200)**

```json
{
  "contacts": [
    {
      "id": 1,
      "name": "山田太郎",
      "email": "taro@example.com",
      "category": "general",
      "message": "お問い合わせ内容です。",
      "created_at": "2026-09-07T10:08:34.616Z"
    }
  ],
  "categories": {
    "general": "一般的なお問い合わせ",
    "product": "製品・サービスについて",
    "quote": "お見積もり・体験のご相談",
    "other": "その他"
  }
}
```

### 3.3 `GET /api/health`

ヘルスチェック用。DB接続の有無に関わらず200を返す。

```json
{ "status": "ok" }
```

## 4. バリデーション仕様 (`server/routes/contact.js` の `validate()`)

サーバー側で以下を検証する（クライアント側のチェックとは独立に必ず実行する）。

| 項目 | 空文字/未入力 | 形式 | 文字数上限 |
|---|---|---|---|
| `name` | エラー | — | 100文字 |
| `email` | エラー | 正規表現 `^[^\s@]+@[^\s@]+\.[^\s@]+$` に一致しないとエラー | 255文字 |
| `category` | エラー | `general`/`product`/`quote`/`other` のいずれか以外はエラー | — |
| `message` | エラー | — | 2000文字 |

文字列以外の値（`null`, `undefined`, 数値, オブジェクト等）は空文字として扱い、例外を投げずにバリデーションエラーとして処理する。各値は前後の空白をトリムしてから検証・保存する。

## 5. データベース仕様

DB: `contact_form_sample` (PostgreSQL 16) / テーブル: `contacts` の1つのみ。

```sql
CREATE TABLE contacts (
  id SERIAL PRIMARY KEY,
  name VARCHAR(100) NOT NULL,
  email VARCHAR(255) NOT NULL,
  category VARCHAR(50) NOT NULL DEFAULT 'other',
  message TEXT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

| カラム | 型 | NULL | デフォルト | 備考 |
|---|---|---|---|---|
| `id` | `SERIAL` | NOT NULL | 自動採番 | 主キー |
| `name` | `VARCHAR(100)` | NOT NULL | なし | |
| `email` | `VARCHAR(255)` | NOT NULL | なし | |
| `category` | `VARCHAR(50)` | NOT NULL | `'other'` | 許容値はアプリ側でのみ検証。DB上のCHECK制約は設けていない |
| `message` | `TEXT` | NOT NULL | なし | |
| `created_at` | `TIMESTAMPTZ` | NOT NULL | `now()` | |

- インデックスは主キー (`id`) のみとしている。
- 定義ファイル: `server/db/init.sql`（`CREATE TABLE IF NOT EXISTS` + 既存テーブル向けの`ALTER TABLE ... ADD COLUMN IF NOT EXISTS`で冪等に適用できる構成）。
- 適用コマンド: `npm run db:migrate`（`server/db/migrate.js`が実行）。

## 6. アーキテクチャ・技術スタック

| レイヤー | 技術 | 役割 |
|---|---|---|
| フロントエンド | 静的HTML/CSS/JS（フレームワークなし、`public/`配下） | フォーム画面・一覧画面のUI |
| バックエンド | Node.js 20 + Express 4（`server/index.js`） | API提供、`public/`の静的配信を兼ねる |
| DBアクセス | `pg` (node-postgres) | PostgreSQLへの接続 |
| コンテナ化 | `Dockerfile` (`node:20-alpine`ベース) | Azure Container Apps向けのイメージ定義 |
| ホスティング | Azure Container Apps (Consumptionプラン、`min-replicas: 0`) | アプリケーション実行基盤 |
| イメージレジストリ | Azure Container Registry (`acrcontactformsamplengkft`) | コンテナイメージの保管先。管理者ユーザーは無効にし、Container Appsはシステム割り当てマネージドIDでPullする構成 |
| データベース | Azure Database for PostgreSQL Flexible Server (Burstable B1ms, PostgreSQL 16) | データ永続化 |
| 環境変数管理 | `dotenv`（ローカル）、Container Appsのsecret（`DATABASE_URL`） | 接続情報の管理 |

主要な依存パッケージ（`package.json`）:
- `express` ^4.19.2
- `pg` ^8.12.0
- `dotenv` ^16.4.5
- `express-rate-limit` ^7.5.1 （7.3節のボット対策で使用）

サーバーは `public/` を静的配信しつつ `/api/*` のAPIも同一プロセス・同一オリジンで提供する。これにより、GitHub Pagesのような別ホスティングとの分離やCORS設定を不要にしている。

### 6.1 ホスティングにAzure Container Appsを採用した経緯

当初はAzure App Service（Node.jsランタイム、ソースコード直接デプロイ）を設計していた。しかし対象サブスクリプションでApp Service Planに必要なコンピューティング(VM)クォータが0に制限されており、リージョンやサブスクリプションを変えても作成できなかった。クォータ増設にはAzureサポートへの申請が必要となる。

同じ「Azure完結」構成を保ったまま、別のクォータ枠で動くAzure Container Apps（Consumption/サーバーレスプラン）に構成を変更した。この変更に伴うアプリケーションコード側の変更は`Dockerfile`の追加のみで、`server/`・`public/`のコードに変更はない。

## 7. デプロイ手順

```bash
# 1. Azure Container Registry でイメージをビルド・プッシュ (ローカルDocker不要)
az acr build --registry <ACR名> --resource-group <リソースグループ> --image contact-form-sample:latest .

# 2. Container Appを作成 (初回のみ)
az containerapp create \
  --name contact-form-sample \
  --resource-group <リソースグループ> \
  --environment <Container Apps環境名> \
  --image <ACR名>.azurecr.io/contact-form-sample:latest \
  --registry-server <ACR名>.azurecr.io \
  --registry-identity system \
  --target-port 3000 \
  --ingress external \
  --min-replicas 0 --max-replicas 1 \
  --secrets "database-url=<Postgres接続文字列>" \
  --env-vars "DATABASE_URL=secretref:database-url"

# 2'. 更新時はイメージを再ビルド後、以下でリビジョンを更新
az containerapp update \
  --name contact-form-sample \
  --resource-group <リソースグループ> \
  --image <ACR名>.azurecr.io/contact-form-sample:latest \
  --revision-suffix <任意の一意な文字列 (例: 日時やビルド番号)>
```

イメージタグを`:latest`のまま更新すると、参照文字列が変わらないためContainer Appsが新しいリビジョンを作成しないことがある。その場合は`--revision-suffix`で明示的に新しいリビジョンを作成する（コミットハッシュ等でイメージタグ自体を一意にする運用であれば本来この操作は不要）。

## 8. 運用・非機能設計

### 8.1 ロギング

- 全リクエストを `METHOD PATH STATUS DURATIONms` 形式で標準出力にログ出力する設計（`server/index.js`）。
- 未処理エラーはリクエストコンテキスト付きでログ出力し、クライアントには汎用エラーメッセージのみ返す。
- `unhandledRejection` / `uncaughtException` はログ出力の上でプロセスを終了する（コンテナオーケストレーターによる再起動を前提とした設計）。
- Container Apps環境のログは、環境作成時に自動生成されるAzure Monitor Log Analyticsワークスペースに送信される。確認方法:
  ```bash
  az containerapp logs show --name contact-form-sample --resource-group <リソースグループ> --tail 50
  ```
  もしくはAzure Portalの対象Container Appの「ログストリーム」「ログ」からも確認できる。

### 8.2 バックアップ

Azure Database for PostgreSQL Flexible Serverの既定設定を採用している:
- 自動バックアップ保持期間: 7日間（ポイントインタイムリストア可能）
- geo冗長バックアップ: 無効（ローカル冗長のみ）。最小構成・低コストを優先した設計判断。

### 8.3 セキュリティ・ボット対策

- PostgreSQL接続はSSL必須（`sslmode=require`相当、`server/db/pool.js`でデフォルト有効）。
- `/list.html` は認証を設けていない設計。個人情報を含むため外部共有しない運用を前提とする。
- ボット対策として以下の2つを実装している（`server/routes/contact.js`）:
  - **honeypotフィールド** (`hp_website`): `public/index.html`に画面上は見えない隠しフィールドを配置する（`display:none`ではなく画面外配置とし、一部botの`display:none`検出を回避する）。値が入っていればbotとみなし、DB保存をスキップして`201`の偽装成功を返す。
  - **レート制限**: `POST /api/contact`を同一IPから10分あたり5回に制限する（`express-rate-limit`）。超過時は`429`を返す。
  - Azure Container Apps はリバースプロキシ配下で動作するため、`server/index.js`で`app.set("trust proxy", true)`を設定し実クライアントIPを取得する構成としている。
  - Google reCAPTCHA等、外部サービスへの連携は設計に含めていない。
- Express配下の`qs`にmoderate severityの既知の脆弱性があるが、本アプリはJSON APIのみ使用しており影響を受ける経路（urlencodedボディの拡張パース）を使用していないため、実害は限定的と評価している。upstream側の修正待ち。

### 8.4 テスト

- 単体テスト（Node組み込み`node:test`、`npm test`で実行）:
  - `tests/contact.validate.test.js` — `validate()`関数のバリデーションロジックを検証。
  - `tests/contact.honeypot.test.js` — `isHoneypotTriggered()`の判定ロジックを検証。
- レート制限・honeypotのAPI実挙動は、ローカルおよび本番(Container Apps)の双方で手動検証している（`curl`による連続送信で`429`・偽装成功`201`の挙動を確認）。
- データベースに接続した状態での結合テスト（`POST/GET /api/contact`の実挙動を自動検証するもの）は、実行環境（テスト用DBの用意方法）の設計を別途行う必要がある。

### 8.5 デプロイフロー

デプロイは7節の手順を手動で実行する運用としている。GitHub Actions等によるCI/CD自動化は設計・構築の対象に含めていない。
