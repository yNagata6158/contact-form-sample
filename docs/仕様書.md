# contact-form-sample 仕様書

最終更新: 2026-09-07 時点の実装内容を反映。

## 1. 概要

静的HTML/CSS/JSのお問い合わせフォームと、Node.js (Express) のAPI、PostgreSQLへのデータ保存を組み合わせたサンプルアプリケーション。デプロイ先はAzure完結（Azure Container Apps + Azure Database for PostgreSQL）。

デプロイ済みURL:
- フォーム: https://contact-form-sample.proudwave-93429adb.japaneast.azurecontainerapps.io/
- 問い合わせ一覧: https://contact-form-sample.proudwave-93429adb.japaneast.azurecontainerapps.io/list.html （認証なし、社内確認用）

## 2. 機能要件

### 2.1 お問い合わせフォーム (`/`, `index.html`)

入力項目:

| 項目 | 種別 | 必須 | 制約 |
|---|---|---|---|
| お名前 (`name`) | テキスト | ○ | 1〜100文字 |
| メールアドレス (`email`) | テキスト (email) | ○ | 1〜255文字、`xxx@yyy.zzz`形式 |
| お問い合わせ種別 (`category`) | プルダウン | ○ | 下記4種のいずれか |
| お問い合わせ内容 (`message`) | 複数行テキスト | ○ | 1〜2000文字 |

お問い合わせ種別の選択肢:

| 値 | 表示ラベル |
|---|---|
| `general` | 一般的なお問い合わせ |
| `product` | 製品・サービスについて |
| `quote` | お見積もり・体験のご相談 |
| `other` | その他 |

送信時の挙動:
1. クライアント側で必須・形式チェック（`public/script.js`）。エラーはフィールドごとにインライン表示。
2. `POST /api/contact` にJSONで送信。
3. 成功 (201) → `thanks.html` （サンクスページ）へ画面遷移。
4. 失敗 → フォーム下部にエラーメッセージを表示（画面遷移なし）。

管理者への通知メール等は**行わない**（DB保存のみ）。

### 2.2 サンクスページ (`/thanks.html`)

送信成功後に遷移する専用ページ。「お問い合わせありがとうございました。」の文言と、フォームへ戻るリンクを表示。

### 2.3 問い合わせ一覧 (`/list.html`)

- `GET /api/contact` の結果を表形式で表示（日時・お名前・メールアドレス・種別・内容、直近50件、新しい順）。
- **認証なし**。小規模な社内・開発確認用途を想定。個人情報を含むためURLの外部共有は禁止。
- `<meta name="robots" content="noindex, nofollow">` で検索エンジンのインデックスを抑制。

### 2.4 想定していない機能

- ユーザー認証・ログイン機能
- 管理者向けメール通知
- 問い合わせへの返信・ステータス管理
- Google reCAPTCHA等の外部サービスを使ったスパム対策 — 現時点ではhoneypot + レート制限で対応 (7.3節参照)。より強力な対策が必要になれば別途検討

## 3. API仕様

ベースURL: デプロイ先のオリジン（例: `https://contact-form-sample.proudwave-93429adb.japaneast.azurecontainerapps.io`）

### 3.1 `POST /api/contact`

お問い合わせを1件保存する。

**リクエスト**

```
Content-Type: application/json
```

```json
{
  "name": "山田太郎",
  "email": "taro@example.com",
  "category": "general",
  "message": "お問い合わせ内容です。",
  "hp_website": ""
}
```

`hp_website` はボット対策のhoneypotフィールド（7.3節参照）。人間のユーザーには見えないため通常は空文字で送信される。省略しても動作する。

**レスポンス (成功時 201)**

```json
{
  "contact": {
    "id": 1,
    "name": "山田太郎",
    "email": "taro@example.com",
    "category": "general",
    "message": "お問い合わせ内容です。",
    "created_at": "2026-09-07T10:08:34.616Z"
  }
}
```

**レスポンス (バリデーションエラー時 400)**

```json
{
  "error": "入力内容に誤りがあります。",
  "fields": {
    "name": "お名前を入力してください。",
    "email": "メールアドレスの形式が正しくありません。",
    "category": "お問い合わせ種別を選択してください。",
    "message": "お問い合わせ内容を入力してください。"
  }
}
```
`fields`にはエラーのある項目のみが含まれる。

**レスポンス (サーバーエラー時 500)**

```json
{ "error": "サーバーエラーが発生しました。" }
```

**レスポンス (レート制限超過時 429)**

```json
{ "error": "送信回数が上限に達しました。しばらく時間をおいて再度お試しください。" }
```
同一IPから10分あたり5回を超えて送信した場合に返る。

**honeypot検知時のレスポンス (201、偽装成功)**

```json
{ "contact": null }
```
`hp_website` に値が入っている場合、実際にはDBへ保存せずこのレスポンスを返す（ボットに検知されたと悟らせないため）。

### 3.2 `GET /api/contact`

保存済みの問い合わせを新しい順に最大50件返す（`list.html`が利用）。

**レスポンス (200)**

```json
{
  "contacts": [
    {
      "id": 1,
      "name": "山田太郎",
      "email": "taro@example.com",
      "category": "general",
      "message": "お問い合わせ内容です。",
      "created_at": "2026-09-07T10:08:34.616Z"
    }
  ],
  "categories": {
    "general": "一般的なお問い合わせ",
    "product": "製品・サービスについて",
    "quote": "お見積もり・体験のご相談",
    "other": "その他"
  }
}
```

### 3.3 `GET /api/health`

ヘルスチェック用。DB接続の有無に関わらず200を返す。

```json
{ "status": "ok" }
```

## 4. バリデーション仕様 (`server/routes/contact.js` の `validate()`)

サーバー側で以下を検証する（クライアント側のチェックとは独立に必ず実行）。

| 項目 | 空文字/未入力 | 形式 | 文字数上限 |
|---|---|---|---|
| `name` | エラー | — | 100文字 |
| `email` | エラー | 正規表現 `^[^\s@]+@[^\s@]+\.[^\s@]+$` に一致しないとエラー | 255文字 |
| `category` | エラー | `general`/`product`/`quote`/`other` のいずれか以外はエラー | — |
| `message` | エラー | — | 2000文字 |

文字列以外の値（`null`, `undefined`, 数値, オブジェクト等）は空文字として扱われ、例外を投げずにバリデーションエラーとして処理される。各値は前後の空白をトリムしてから検証・保存する。

## 5. データベース仕様

DB: `contact_form_sample` (PostgreSQL 16) / テーブル: `contacts` の1つのみ。

```sql
CREATE TABLE contacts (
  id SERIAL PRIMARY KEY,
  name VARCHAR(100) NOT NULL,
  email VARCHAR(255) NOT NULL,
  category VARCHAR(50) NOT NULL DEFAULT 'other',
  message TEXT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

| カラム | 型 | NULL | デフォルト | 備考 |
|---|---|---|---|---|
| `id` | `SERIAL` | NOT NULL | 自動採番 | 主キー |
| `name` | `VARCHAR(100)` | NOT NULL | なし | |
| `email` | `VARCHAR(255)` | NOT NULL | なし | |
| `category` | `VARCHAR(50)` | NOT NULL | `'other'` | 許容値はアプリ側でのみ検証。DB上のCHECK制約なし |
| `message` | `TEXT` | NOT NULL | なし | |
| `created_at` | `TIMESTAMPTZ` | NOT NULL | `now()` | |

- インデックスは主キー (`id`) のみ。
- 定義ファイル: `server/db/init.sql`（`CREATE TABLE IF NOT EXISTS` + 既存テーブル向けの`ALTER TABLE ... ADD COLUMN IF NOT EXISTS`で冪等に適用可能）。
- 適用コマンド: `npm run db:migrate`（`server/db/migrate.js`が実行）。

## 6. アーキテクチャ・技術スタック

| レイヤー | 技術 |
|---|---|
| フロントエンド | 静的HTML/CSS/JS（フレームワークなし、`public/`配下） |
| バックエンド | Node.js 20 + Express 4（`server/index.js`） |
| DBアクセス | `pg` (node-postgres) |
| データベース | Azure Database for PostgreSQL Flexible Server (Burstable B1ms, PostgreSQL 16) |
| コンテナ化 | `Dockerfile` (`node:20-alpine`ベース) |
| ホスティング | Azure Container Apps (Consumptionプラン、`min-replicas: 0`) |
| イメージレジストリ | Azure Container Registry（管理者ユーザー無効、Container Appsはシステム割り当てマネージドIDでPull） |
| 環境変数管理 | `dotenv`（ローカル）、Container Appsのsecret（`DATABASE_URL`） |

主要な依存パッケージ（`package.json`）:
- `express` ^4.19.2
- `pg` ^8.12.0
- `dotenv` ^16.4.5
- `express-rate-limit` ^7 （ボット対策のレート制限、7.3節参照）

サーバーは `public/` を静的配信しつつ `/api/*` のAPIも同一プロセス・同一オリジンで提供するため、GitHub Pagesのような別ホスティングとの分離やCORS設定は不要な構成になっている。

### なぜApp ServiceではなくContainer Appsか

当初はAzure App Serviceを想定していたが、対象サブスクリプションでコンピューティング(VM)クォータが0に制限されており作成できなかった。ポータルでのクォータ増設申請が煩雑なため、同じ「Azure完結」構成のまま、別のクォータ枠で動くAzure Container Apps（Consumption/サーバーレスプラン）に変更した。詳細は `README.md` を参照。

## 7. 運用・非機能面

### 7.1 ロギング

- 全リクエストを `METHOD PATH STATUS DURATIONms` 形式で標準出力にログ出力（`server/index.js`）。
- 未処理エラーはリクエストコンテキスト付きでログ出力し、クライアントには汎用エラーメッセージのみ返す。
- `unhandledRejection` / `uncaughtException` はログ出力の上でプロセスを終了する（コンテナオーケストレーターによる再起動を前提とした設計）。
- Container Apps環境のログはAzure Monitor Log Analyticsワークスペースに自動送信される。

### 7.2 バックアップ

Azure Database for PostgreSQL Flexible Serverの既定設定を採用:
- 自動バックアップ保持期間: 7日間（ポイントインタイムリストア可能）
- geo冗長バックアップ: 無効（ローカル冗長のみ、低コスト優先のトレードオフ）

### 7.3 セキュリティ

- PostgreSQL接続はSSL必須（`sslmode=require`相当、`server/db/pool.js`でデフォルト有効）。
- `/list.html` は認証なし。個人情報を含むため外部共有しない運用を前提とする。
- **ボット対策** (`server/routes/contact.js`):
  - **honeypotフィールド** (`hp_website`): `public/index.html`に画面上は見えない隠しフィールドを配置 (`display:none`ではなく画面外配置。一部botの`display:none`検出を回避)。値が入っていればbotとみなし、DB保存をスキップして`201`の偽装成功を返す。
  - **レート制限**: `POST /api/contact`を同一IPから10分あたり5回に制限（`express-rate-limit`）。超過時は`429`。
  - Azure Container Apps はリバースプロキシ配下のため、`server/index.js`で`app.set("trust proxy", true)`を設定し実クライアントIPを取得。
  - Google reCAPTCHA等の外部サービス連携は未実装。より強力な対策が必要になれば検討。
- 監視アラート（エラー率上昇時の通知など）は未設定（[Issue #4](https://github.com/yNagata6158/contact-form-sample/issues/4)）。
- 既知の脆弱性: Express配下の`qs`にmoderate severityの既知の脆弱性があるが、upstream未パッチ。JSON APIのみ使用しており実害は限定的と判断し監視継続中。

### 7.4 テスト

- 単体テスト（Node組み込み`node:test`、`npm test`で実行）:
  - `tests/contact.validate.test.js` — `validate()`関数のバリデーションロジックを8ケースで検証。
  - `tests/contact.honeypot.test.js` — `isHoneypotTriggered()`の判定ロジックを5ケースで検証。
- レート制限・honeypotのAPI実挙動は、ローカル環境および本番 (Container Apps) の両方で手動検証済み（`curl`で6回連続送信し5回目以降が`429`になること、honeypot発火時にDB非保存で`201`偽装成功になることを確認）。自動テスト化は未実施。
- 結合テスト（DBに依存する`POST/GET /api/contact`の実挙動）は未整備（[Issue #2](https://github.com/yNagata6158/contact-form-sample/issues/2)）。
